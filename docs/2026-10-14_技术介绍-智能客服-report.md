# 铁路购票系统智能客服模块介绍

## 一、模块概述

本项目在铁路购票系统中设计并实现了智能客服模块，结合大语言模型、业务工具调用和检索增强生成（Retrieval-Augmented Generation，RAG），为用户提供自然语言形式的业务咨询服务。

用户可以直接输入有关车票、订单、车站或购票规则的问题。系统根据问题选择相应的业务工具或知识库检索工具，取得查询结果后，再由大语言模型组织成易于理解的文字回复。对话过程中保留必要的历史上下文，支持用户继续追问。

模块的设计重点是将模型的语言理解能力与购票系统的真实数据、业务权限和知识管理机制结合起来。车次与订单信息由业务服务提供，铁路规则由维护的知识库提供，模型负责理解需求、选择工具和表达结果。项目使用现成模型开展推理，不涉及基础语言模型的训练或微调。

## 二、设计背景与目标

铁路购票平台涉及车次查询、座席选择、订单状态、支付退款、乘车证件等业务。对于不熟悉系统的用户，仅依靠菜单和固定帮助文档，往往需要在多个页面之间寻找答案。

业务问题还具有不同的数据来源和时效性。例如，某趟车是否有二等座，需要读取当前车票数据；某个订单是否已支付，需要读取当前用户的订单；学生票条件、退改规则等问题则需要参考业务知识文档。若统一依赖模型自身的记忆回答，容易出现数据过期、规则不准确或信息来源不明确的问题。

因此，本模块设置了五项主要目标：

1. 支持自然语言咨询，减少用户理解业务页面和术语的成本。
2. 将实时问题连接到业务查询服务，将规则问题连接到知识库检索服务。
3. 支持多轮对话，使用户能够围绕同一问题连续补充条件和追问。
4. 在后端校验用户身份、订单归属和会话归属，保护用户的业务信息。
5. 提供流式展示、超时处理、限流和取消机制，使模型能力能够稳定接入 Web 应用。

这些目标是系统设计与实现的目标。目前已完成主要功能及定向联调，用户效率提升和回答质量仍需要后续实验量化。

## 三、当前功能范围

| 功能 | 主要输入 | 处理方式 | 用户可获得的信息 |
| --- | --- | --- | --- |
| 车票查询 | 出发站、到达站、出发日期 | 调用车票业务服务 | 车次、出发时间、席别、票价和余票 |
| 订单查询 | 订单号、当前登录身份 | 查询订单并校验归属 | 当前用户的订单状态、车次及起讫站 |
| 车站查询 | 车站名称或拼音关键词 | 查询车站基础数据 | 车站名称、拼音、所属区域 |
| 业务知识咨询 | 自然语言问题 | 调用混合检索工具 | 根据知识片段解释退改、购票、证件等规则 |
| 多轮追问 | 当前问题与会话标识 | 加载本用户会话历史 | 围绕上文继续补充条件、追问和解释 |
| 会话管理 | 当前登录身份 | 查询或删除本用户会话 | 历史列表、消息详情及工具结果 |
| 知识库维护 | 分类、文档或切片内容 | 解析、切片、向量化与管理接口 | 支持知识内容更新、检索测试和入库任务查看 |

当前客服向模型开放四个只读工具：`queryTicket`、`queryOrder`、`queryStation`、`searchKnowledge`。购票、支付、取消和退款通过系统的独立业务流程执行；客服可以查询、解释和引导操作，目前没有向模型开放自动下单或直接退款工具。

## 四、技术架构与技术选型

模块与购票业务共同运行在 Spring Boot 单体应用中，内部按对话编排、工具执行、知识检索、文档入库和会话持久化划分职责。该划分保留了清晰的模块接口，便于测试和后续替换模型服务。

| 层次 | 当前技术或组件 | 职责 |
| --- | --- | --- |
| 用户交互层 | Vue 3、TypeScript、Element Plus | 客服浮窗、输入、流式显示、历史查看和工具过程展示 |
| 服务编排层 | Spring Boot 3、Java、独立线程池 | 身份检查、上下文装配、模型调用及任务生命周期管理 |
| 工具执行层 | Function Calling、自定义工具注册与执行引擎 | 工具定义、参数处理、白名单查找和受控业务调用 |
| 生成模型层 | 当前配置为 DeepSeek，通过 OpenAI 兼容接口访问 | 理解问题、提出工具调用、根据结果生成回复 |
| 向量模型层 | 本地 Ollama、qwen3-embedding:0.6b | 将问题和知识切片转换成 1024 维向量 |
| 数据与检索层 | PostgreSQL、pgvector、MyBatis-Plus | 业务数据查询、会话保存、向量检索和关键词检索 |
| 资源控制层 | Redis、Redisson、进程内并发限制 | 用户提问限流、摘要锁和请求并发控制 |
| 文档处理与存储层 | Apache Tika、Markdown 解析器、S3 兼容对象存储 | 提取文档文本、保存原文件、管理入库任务 |
| 流式通信层 | HTTP POST、SSE、前端 Fetch 流读取 | 逐片段发送答案、工具事件、完成事件和错误事件 |

生成模型和向量模型分开配置，便于分别调整回答能力与检索能力。模型客户端使用兼容接口，降低了业务模块对某一模型供应商的依赖。这个接口设计提供替换条件，但不代表所有兼容服务都已完成实际适配验收。

## 五、业务工具调用的工作流程

一次对话的主要流程如下：

1. 用户通过客服浮窗提交问题和可选的会话标识，前端携带登录令牌。
2. 后端校验登录身份，检查问题长度、提问频率和并发限制，并检查会话是否属于该用户。
3. 后端读取会话历史，每轮重新加入客服系统规则，再追加用户的新问题。
4. 将上下文与四个工具的定义发送给模型。工具定义包含工具名称、用途、参数类型及必填项。
5. 模型返回文本或工具调用请求。若返回工具调用，后端从注册的工具中查找对应执行器，解析参数并执行业务查询。
6. 查询结果作为工具消息加入上下文，再次调用模型，让模型根据这些结果继续处理问题或生成最终答案。
7. 最终回复按文本片段推送至前端；后端保存本轮用户消息、工具请求、工具结果和最终答案，保存完成后发送会话完成事件。

例如，用户询问“2026 年 10 月 15 日北京南到上海虹桥有没有二等座”。模型需要提取出发站、到达站和日期，调用 `queryTicket`。业务服务按日期查询车次及余票，将结果返回模型。模型再将查询结果整理成自然语言说明。

对于参数不完整的问题，例如“帮我查一下去上海的车票”，系统提示词要求模型先询问缺失条件。后端工具也会检查必要参数，缺少条件时返回错误信息。系统提示词用于引导模型行为，实际身份与权限约束由后端代码执行。

引擎最多执行五轮模型迭代，限制工具循环次数；单次工具执行等待上限为十秒。未知工具、参数错误、查询异常和执行超时会转换成工具错误结果，交给模型组织说明。工具任务使用有容量限制的独立线程池；超时和取消时会请求中断任务，具体执行是否立即停止仍取决于数据库驱动或其它被调用组件对中断的支持。

## 六、知识库与 RAG 的实现

### 6.1 文档入库

管理员可以维护知识分类并上传业务文档。后台执行“原文件保存—文本解析—切片—向量化—切片存储”的入库流程，并记录任务状态和已处理切片数量。

Markdown 使用专用解析器提取文本；Word、带文本层的 PDF 等格式通过 Apache Tika 提取文本。当前代码还包含对 Excel 类型的解析支持。扫描件 OCR 仍是占位实现，因此不能把纯图片 PDF 的识别能力作为已完成能力介绍。

系统提供两类切片策略：

- 固定长度切片：按字符预算拆分文本，并保留相邻切片之间的重叠内容。
- 结构感知切片：识别 Markdown 标题层级，保留章节上下文，再依据长度预算拆分或合并段落。

结构感知策略的默认目标长度约为 500 字符，最大长度约为 1000 字符，重叠长度约为 128 字符。这些是字符预算，并不是严格的模型 token 数。

切片完成后，本地向量模型将各片段转换成向量，与文本、文档标识、分类和切片序号一同写入 PostgreSQL。原文件与检索切片分开保存，便于文档管理与检索更新。

### 6.2 混合检索

知识咨询由 `searchKnowledge` 工具进入检索流程。系统首先对问题进行向量化，然后分别执行向量检索和关键词检索。

向量通道使用 pgvector 的余弦距离进行近邻查询，适合处理用户表达与知识文档措辞不完全一致的情况。关键词通道先尝试完整文本匹配；未命中时，使用中文相邻双字词项及完整英文、数字标识进行召回。例如“学生票怎么买”可以提取“学生”“生票”等词项，以匹配“学生票购买条件”。这种词项拆分是轻量实现，并非成熟的中文分词模型。

两路结果通过 RRF（Reciprocal Rank Fusion）按排名融合。当前使用的形式为：

```text
融合分数 = Σ 1 / (60 + 该通道中的排名)
```

该方法依据排名合并候选，避免直接比较向量相似度与关键词匹配的不同分值。客服入口每路候选数量为五，融合和排序后最多取三个候选。

代码提供了重排序接口，便于接入专门的 rerank 服务。当前配置关闭了模型重排序，实际使用按融合分数排序的兜底实现，不能将“已启用神经网络重排序”作为当前成果。

### 6.3 上下文扩展与回复生成

系统对最终候选扩展前后各一个相邻切片，并对重复邻居进行去重。这样可以在命中某个规则条款时，一并带回附近的适用条件或例外说明，减少只读取孤立片段带来的误解。

知识片段及分数作为工具结果返回模型，由模型结合问题生成解释。前端能够查看检索片段和工具结果，便于用户核对答案参考了哪些内容。目前展示的是片段级来源，文档标题、章节定位和逐句引用仍有完善空间。

系统提示词要求：对于规定需要知识查询的问题先使用知识库；未取得知识依据时，不自行给出具体手续费、比例、时限或证件规则。该设计旨在减少无依据回答，但检索到候选本身不等于候选一定相关，也不能保证模型完全不产生错误。相关性阈值、拒答效果和引用准确率还需要专门评测。

目前检索结果直接读取知识库，没有复用旧的问答检索结果缓存。联调已确认，文档切片更新后再次提问会读取新内容，文档删除后不再被查询到。这样保证了本次测试中的更新可见性，代价是重复问题会重新执行检索和向量化。

## 七、多轮对话与历史管理

会话使用独立标识管理。用户可以创建新会话、查看历史消息、恢复已有会话继续追问或删除本人的会话。

系统在进入对话、读取历史和追加记录时检查会话归属，避免用户通过更换会话标识读取或写入其他用户的历史。模型上下文中的订单信息，也需要经订单查询工具的归属校验后才能返回。

每轮保存的不只是用户和客服的最终文字，还包括 assistant 提出的工具调用列表、每次调用的 ID、参数和对应工具结果。历史恢复时保留工具请求与结果的对应关系，使下一轮模型能够正确理解前一轮查询过程。对旧记录或截断造成的孤立工具消息，系统会过滤不完整的调用序列，避免把无对应请求的工具结果发送给模型。

当前会话加载最近二十条消息；内容估算超过约两千 token 时，会尝试生成摘要。摘要操作使用 Redisson 锁，并记录摘要覆盖的消息水位线，恢复时组合摘要与水位线后的消息。token 数采用启发式估算，摘要机制主要用于控制上下文开销；长期记忆完整性和多次摘要后的信息保留效果尚未经过系统评估。

客服系统提示词与会话历史分开管理，并在每轮对话中重新加载。这样可以在多轮追问时持续提供工具使用要求和回答规则。

## 八、流式交互与资源控制

前端通过 Fetch 提交 POST 请求，并读取 SSE 事件流。使用 POST 能同时携带问题、会话标识与身份信息。服务端将模型文本按片段推送，用户可以在完整答案生成前开始阅读。

除回复文本外，事件流还包含工具调用提示、工具名称、参数、查询结果、知识片段、完成标识和错误说明。界面中的过程展示属于可展示的状态提示与工具执行记录，不应等同于模型内部的完整推理过程。

为避免用户关闭页面后后台任务继续消耗资源，模块设置了取消链路：关闭客服浮窗、切换会话、页面卸载等操作会中止前端请求；服务端在检测到断连、发送失败或超时时取消工作任务，并关闭正在读取的模型响应流。工具任务也注册取消处理，并通过中断请求停止执行。

当前配置中，每个用户每分钟最多发起三十条消息，同一用户同时处理一个请求，应用进程内全局最多处理三十二个请求。SSE 连接上限为六十秒，并定期发送心跳。模型连续失败达到阈值时，健康状态管理进入熔断状态，等待恢复探测。

其中 Redis 负责跨请求的用户频率限制，用户和全局并发限制主要在应用进程内实现。若未来部署多个应用实例，需要进一步统一并发预算，不能直接把当前限制当作集群范围内的严格并发上限。

## 九、权限与业务边界

模块的权限控制覆盖三个层次：

1. 登录校验：通过登录令牌和 Redis 登录态确认用户身份。
2. 会话校验：读取、继续对话、保存和删除历史时，以登录用户与会话所有者的关系进行校验。
3. 订单校验：订单查询工具使用后端传入的用户身份，验证订单是否属于该用户。

工具名称必须存在于注册表中，工具执行由后端实现。模型只能提出已开放能力的调用请求，不能自行执行数据库修改或调用未注册的业务方法。

此外，订单工具只返回当前实现所需的订单号、状态、车次和起讫站等关键字段，降低在模型上下文中携带不必要个人信息的数量。涉及真实部署时，还需要对发往外部模型服务的对话与业务数据建立明确的数据使用和隐私说明。

## 十、项目特色与毕业设计工作量

本模块的主要特色可以概括为五个方面。

第一，将业务工具查询与知识库检索放在统一的对话流程中。系统根据问题调用不同的数据来源，处理实时业务信息与相对稳定的业务规则。

第二，为铁路业务场景设计了工具参数、身份上下文和返回字段，使模型调用能够与现有业务服务衔接。

第三，实现了向量与关键词混合召回、排名融合、结构感知切片和邻居扩展，围绕规则文档的结构进行检索处理。

第四，完整保存工具调用协议和最终回复，并在恢复历史时处理不完整记录，支撑真实多轮工具对话。

第五，围绕 Web 交互加入流式展示、历史管理、取消、超时、限流、并发控制和模型熔断，使客服功能具有可演示、可测试的工程闭环。

真实联调使用了当前模型服务、PostgreSQL/pgvector、Redis、本地 Ollama 以及项目后端，并使用独立测试账号和临时知识文档。

其中，多轮测试确认用户提供的唯一代号能在下一轮被回答；跨账号传入会话标识时，读取和追加被拒绝；真实车站工具查询及后续追问能够完成，工具调用 ID 在数据库中得到保存。

知识更新测试在隔离文档中写入“测试额度为 37 公斤”，随后将其改为“42 公斤”。再次检索和重新提问读取了新值，删除文档后分类检索为空。该数值只是测试标记，不是铁路政策。

本轮短请求中，记录到的成功回复首片段等待时间大致为 0.8—3.5 秒。这是特定环境下的少量样本，受到工具调用和模型负载影响，不能作为固定响应承诺或完整性能指标。

## 十四、简要表述

本项目实现了一个面向铁路购票场景的智能客服模块，采用大语言模型、Function Calling 和 RAG 相结合的技术方案。模型根据用户的自然语言需求调用车票、订单、车站或知识检索工具，由业务服务和知识库提供实际数据，再生成文字说明。系统实现了混合检索、结构感知切片、邻居上下文扩展、多轮会话持久化、会话与订单权限检查，以及流式回复、取消、超时和限流控制。目前主要功能已完成，已通过定向回归、真实模型接口联调和浏览器验证。后续重点是建立业务问题评测集，量化检索效果、回答准确性和响应性能，并完善长会话与并发场景。
