# 智能客服压测报告

## 测试时间

2026-08-01

## 测试目标

验证智能客服在接入 DeepSeek 云端聊天模型与本地 Ollama 向量模型后的真实并发表现，重点关注：

- 登录态与 SSE 流式响应是否稳定
- Function Calling 工具调用是否稳定
- RAG 检索链路是否能在小并发下正常返回来源
- 单用户并发限制与全局并发限制是否生效
- 服务在压测后是否保持健康

## 测试环境

- 后端服务：Spring Boot，端口 `8080`
- 数据库：PostgreSQL，健康检查 `UP`
- 缓存：Redis，健康检查 `UP`
- 聊天模型：DeepSeek `deepseek-v4-flash`
- 向量模型：Ollama `qwen3-embedding:0.6b`
- Ollama 地址：`http://127.0.0.1:11434`
- Rerank：未启用，当前使用 `NoopRerankClient`

## 压测配置

```yaml
ai:
  chat:
    rate-limit-per-minute: 30
    worker-core-size: 8
    worker-max-size: 32
    worker-queue-capacity: 128
    global-max-concurrent: 32
    user-max-concurrent: 1

    max-concurrent: 4
```

## 并发保护验证

### 单用户并发限制

场景：同一账号 3 个并发请求。

| 指标 | 结果 |
| --- | --- |
| 请求数 | 3 |
| 正常完成 | 1 |
| 快速拒绝 | 2 |
| 拒绝耗时 | 约 57ms |

结论：`user-max-concurrent=1` 生效，能避免单个账号同时占用多个 AI 客服执行槽位。

### 全局并发限制

保守配置 `global-max-concurrent=8` 时，12 个定时同时请求中：

| 指标 | 结果 |
| --- | --- |
| 请求数 | 12 |
| 正常完成 | 8 |
| 快速拒绝 | 4 |
| 拒绝耗时 | 约 72-84ms |

结论：全局并发闸门生效，超出容量后快速失败，避免请求无限堆积。

## 放宽配置后的阶梯压测

| 场景 | 并发 | 成功 | 错误 | 平均耗时 | P95 / 最大耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 普通聊天 | 16 | 16 | 0 | 6.4s | 12.0s |
| 普通聊天 | 32 | 32 | 0 | 12.5s | 15.9s / 16.5s |
| 车站工具调用 `queryStation` | 16 | 16 | 0 | 3.16s | 5.16s |
| RAG 退票规则 `searchKnowledge` | 8 | 8 | 0 | 13.05s | 14.78s |

压测后 `/actuator/health` 仍为 `UP`，PostgreSQL 与 Redis 均正常。

## 结论

当前智能客服在中等并发配置下表现稳定：

- 可以稳定承受 32 并发普通聊天。
- 可以稳定承受 16 并发业务工具调用。
- 可以稳定承受 8 并发 RAG 检索。
- 单用户并发保护与全局并发保护均生效。
- SSE 返回结构完整，包含 `thinking`、`tool_call`、`tool_result`、`token`、`done` 等事件。
- RAG 命中后能够返回知识来源 `sources`。

主要瓶颈在 RAG 场景，链路包括：

```text
DeepSeek 判断工具调用
-> 本地 Ollama embedding
-> PGVector / 关键词检索
-> 工具结果返回
-> DeepSeek 二次总结
```

因此 RAG 场景平均耗时高于普通聊天和普通业务工具调用。

## 建议

- 演示环境可以保留当前中等压测配置。
- 如果机器资源紧张，可将 `global-max-concurrent` 调回 `8-16`。
- RAG 并发不建议直接拉到 32，除非改用云端 embedding、增强 RAG 缓存，或将 RAG 检索与模型总结进一步拆分。
- 后续可在 OpenAI 兼容请求体中增加 DeepSeek `user_id` 参数，用业务侧非隐私用户 ID 实现内容安全隔离、KVCache 隔离和调度隔离。
